# NodeShare Security & Architecture Guide

## 1. Threat Model & Security Posture

Security is critical to NodeShare. NodeShare enables private peer-to-peer and group communications and file sharing across Windows desktop and Android devices. This document outlines the defense-in-depth measures implemented across the application.

---

## 2. Authentication & Credential Storage

### Argon2id Password Hashing
- **Algorithm**: Argon2id (`Type.ID`)
- **Memory Cost**: `65536 KiB` (64 MB)
- **Time Cost**: `3 iterations`
- **Parallelism**: `4 threads`
- **Hash Length**: `32 bytes`
- **Protection**: Resists both side-channel cache-timing attacks and GPU-accelerated cracking. Plaintext passwords are never logged, echoed, or stored.

### Access & Refresh Token Lifecycle
- **Access Tokens**: Short-lived (15 minutes), signed with HMAC-SHA256 (`HS256`) using a minimum 32-byte secret key.
- **Refresh Tokens**: Opaque 64-byte cryptographically secure random strings (`secrets.token_urlsafe(64)`).
- **Hashed Token Storage**: The raw refresh token is returned to the client once. Only its SHA-256 hash is persisted in the database. A database dump does not expose active session tokens.
- **Token Rotation & Family Revocation**: Every token refresh operation rotates the token by revoking the old one and issuing a new one. If an already-revoked refresh token is presented (indicating theft or token reuse), **all sessions for that user account are instantly revoked**.
- **Password Change Invalidation**: Changing the password immediately revokes all active refresh tokens.

## 3. Database Isolation & IDOR Prevention

### Clear Separation of Concerns
1. **Supabase PostgreSQL** holds authoritative relationship metadata:
   - User identities and usernames
   - Friendships, blocks, and requests
   - Conversation participants
   - Group memberships and roles (`owner`, `admin`, `member`)
   - Storage metadata and quotas
2. **MongoDB Atlas** stores high-throughput chat messages:
   - Text messages, reactions, replies, edit histories, delivery metadata.

### Mandatory Access Control Before Message Access
- Before querying or inserting messages into MongoDB, the backend **always verifies conversation membership in Supabase PostgreSQL**:
  ```python
  is_member = await ConversationService.verify_conversation_membership(conversation_id, user_id)
  if not is_member:
      raise HTTPException(status_code=403, detail="Forbidden")
  ```
- Users cannot access, query, or append messages to conversations or groups they do not belong to, preventing Insecure Direct Object Reference (IDOR) attacks.

### SQL & NoSQL Injection Protection
- **PostgreSQL**: All queries use strict positional parameterized binding (`$1, $2, ...`) via `asyncpg`. No string concatenation or string interpolation is permitted in SQL statements.
- **MongoDB**: All queries use strongly-typed Pydantic schemas and strict dictionary field lookups.

## 4. File Upload & Storage Security

### Direct-to-Storage Architecture
- Large file uploads **never traverse Vercel serverless functions**, protecting serverless memory and platform limits.
- Pre-signed upload URLs are generated by Supabase Storage and delivered to authenticated clients.

### Multi-Stage Validation
1. **Extension Allowlist**: Only authorized file extensions (`.jpg`, `.png`, `.webp`, `.gif`, `.mp4`, `.webm`, `.mp3`, `.wav`, `.pdf`, `.txt`, `.docx`, `.xlsx`, `.zip`) are accepted. Executables (`.exe`, `.bat`, `.sh`, `.cmd`, `.msi`) are rejected.
2. **MIME Type Validation**: Rejects untrusted MIME types.
3. **Magic Bytes Signature Check**: `validate_file_signature()` checks file magic headers via `filetype` to detect spoofed extensions (e.g., an `.exe` renamed to `.png`).
4. **Size & Quota Enforcement**:
   - Max file size: 100 MB per file.
   - User storage quota: 1 GB cumulative per user account.

## 5. Network & API Protection

### Sliding-Window Rate Limiting
- **General Endpoints**: 120 requests/minute per IP.
- **Authentication Endpoints** (`/api/auth/login`, `/api/auth/register`): 10 requests/minute per IP with automatic HTTP 429 response and `Retry-After: 60` headers.

### Security Response Headers
Every response includes:
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `X-XSS-Protection: 1; mode=block`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Content-Security-Policy: default-src 'none'; frame-ancestors 'none';`
- `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload` (in production)

### CORS Whitelisting
- Strict origin allowlist configured via `CORS_ORIGINS`.
- Wildcard `*` origins are prohibited when `allow_credentials=True`.

## 6. Pre-Deployment Production Checklist

- [ ] Generate a production `JWT_SECRET_KEY` with `python -c "import secrets; print(secrets.token_hex(32))"`.
- [ ] Set `ENVIRONMENT=production` and `DEBUG=False`.
- [ ] Connect `SUPABASE_POSTGRES_URL` to transaction pooler port `6543`.
- [ ] Ensure Supabase Storage bucket `nodeshare-files` is marked **Private**.
- [ ] Configure MongoDB Atlas IP Access List (allow serverless access or VPC peering).
- [ ] Set up client origins in `CORS_ORIGINS`.
- [ ] Never commit `.env` or secrets to version control.
